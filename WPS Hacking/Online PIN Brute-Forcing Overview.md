
One of the ways that we can attempt to retrieve the correct WPS pin for a target network is through online PIN brute-forcing. This can be conducted with a few different tools, but popularly it is done with either Reaver or Bully.

![Diagram showing WPA-PSK communication between Attacker and Access Point. Attacker attempts with sequences 0000001, 0000002, and succeeds with 0000003.](https://cdn.services-k8s.prod.aws.htb.systems/content/modules/186/BruteForcing/Online/WPS_BRUTE.png)

Online brute-forcing works by trying all possible digit combinations and sending them to the access point for verification. By doing this, we go through the series of EAP messages for each possible PIN. In the M4 message, the client sends the access point the R-Hash1 and R-Hash2 values, along with the R-S1 nonce values encrypted with AES. During this message, the access point computes the received R-Hash1 and R-Hash2 values to verify if the PIN we sent is correct. If it is, the remaining messages are exchanged. If it is not, we receive a NACK.


### The PIN split

The 8-digit PIN isn’t checked as one unit. It’s split in half:

- **PSK1** = first 4 digits
- **PSK2** = remaining 3 digits (the 8th digit is a checksum, not entropy)

This split is exactly why WPS PINs are weak: instead of brute-forcing ~10^8 combinations, you brute-force ~10^4 (10,000) for the first half, then ~10^3 (1,000, minus checksum) for the second half — roughly 11,000 combinations total, which the text references.

### The hash commitment scheme (E-Hash / R-Hash)

Both sides prove they know their half of the PIN using a **hash-commitment** structure, built from Diffie-Hellman key agreement plus nonces:

- **PKe / PKr**: Diffie-Hellman public keys — PKe from the “Enrollee” (client, i.e., your attacking tool pretending to register), PKr from the “Registrar” role your tool is playing when attacking (confusing naming, but essentially: each side has a DH keypair, and from these a shared secret is derived).
- **E-S1/E-S2** and **R-S1/R-S2**: 128-bit random nonces generated by the Enrollee (E) side and Registrar (R) side respectively, one nonce per PIN-half.
- **E-Hash1/E-Hash2** and **R-Hash1/R-Hash2**: HMAC-style hashes computed over (nonce + PSK-half + public keys + authkey). Critically, the hash is sent _before_ the nonce — this is the “commit” step. The nonce is only revealed afterward (in a later message), which is the “reveal” step — a standard commitment scheme so neither side can lie about already knowing the answer after seeing the other’s data.

### Walking through the attack

In an online brute-force (what tools like Reaver do):

1. **M3** — The AP sends you **E-Hash1** and **E-Hash2**, which are commitments based on the real PSK1/PSK2 (which you don’t know yet) and the AP’s secret nonces E-S1/E-S2 (which you also don’t know yet).
2. You, as attacker, generate your own DH keypair (**PKr**), your own nonces **R-S1/R-S2**, and you _guess_ a PIN half.
3. Using your guessed PSK1/PSK2, you compute **R-Hash1/R-Hash2** — your own commitments — and send them in **M4** along with R-S1/R-S2 (actually R-S1 goes in M4, R-S2 in M6, since the two halves are verified sequentially).
4. **The AP now checks**: it recomputes what R-Hash1 _should_ be, using the real PSK1 and your revealed R-S1/PKr. If your guessed PSK1 matches the real one, the hash matches, and the AP proceeds to M5. If not, you get an **EAP-NACK** immediately, and you know that PIN-half guess was wrong.
5. If you got PSK1 right, the AP sends **M5**, which contains **E-S1** — the real nonce for the first half — letting you verify the AP isn’t cheating and confirming your guess was correct.
6. The same process repeats for the second half (PSK2) in M6/M7, with **E-S2** revealed in **M7** if correct.
7. If both halves check out, the AP proceeds to send the actual **WPA-PSK**, encrypted, in **M7/M8**.

### E-S1 / E-S2 and R-S1 / R-S2 (the nonces)

These are **128-bit random numbers** (nonces = “numbers used once”), generated independently by each side of the handshake:

- **E-S1, E-S2** — generated by the **Enrollee** (the device trying to join the network / register). One nonce for each half of the PIN: E-S1 corresponds to PSK1 (first 4 PIN digits), E-S2 corresponds to PSK2 (last 3 PIN digits + checksum).
- **R-S1, R-S2** — generated by the **Registrar** (the device that already knows the network credentials and is authorizing the new device — normally the AP itself acting as Registrar, or in an attack scenario, your tool pretending to be the Registrar).

Their only job is to act as a **random blinding factor** fed into a hash, so that the hash commitment (see below) can’t be precomputed or reused across sessions — each run of the protocol uses fresh nonces, so the same PIN produces different hash values every time.

### E-Hash1 / E-Hash2 and R-Hash1 / R-Hash2 (the commitments)

These are **HMAC-SHA256 values** computed over a combination of:

- the relevant nonce (E-S1 or E-S2 for E-Hash; R-S1 or R-S2 for R-Hash)
- the relevant PIN half (PSK1 or PSK2)
- both sides’ Diffie-Hellman public keys (PKe, PKr)
- an “AuthKey” derived earlier in the exchange from the DH shared secret

Conceptually:

E-Hash1 = HMAC-AuthKey( E-S1 || PSK1 || PKe || PKr )
E-Hash2 = HMAC-AuthKey( E-S2 || PSK2 || PKe || PKr )
R-Hash1 = HMAC-AuthKey( R-S1 || PSK1 || PKe || PKr )
R-Hash2 = HMAC-AuthKey( R-S2 || PSK2 || PKe || PKr )
